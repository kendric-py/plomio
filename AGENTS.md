# AGENTS.md

Этот файл — точка входа в архитектуру и доменные правила SMPCrawl. Подробности по темам ниже вынесены
в отдельные файлы в [`docs/reference/`](./docs/reference), чтобы этот файл оставался обзорным.

Правила по конкретным приложениям — в их собственных `AGENTS.md` (`apps/<app>/AGENTS.md`).

## Что такое SMPCrawl

Сервис для парсинга данных с маркетплейсов (сейчас: **OZON**, **Wildberries**). Клиент ставит задачу
через фронтенд (или API), задача исполняется воркерами-парсерами, результат сохраняется в PostgreSQL
и отдаётся обратно клиенту.

## Домен: задачи

Есть два типа задач:

- **Единоразовые** — выполняются один раз, результат хранится **7 дней**. Реализовано в
  [`packages/task`](./packages/task/AGENTS.md).
- **Периодические** — выполняются с заданной периодичностью, срок хранения результатов задаёт администратор.
  Пример периодической задачи — **мониторинг цены**: указывается ссылка на товар, порог падения цены
  (при достижении которого отправляется уведомление в Telegram) и периодичность проверки. Реализовано
  в [`packages/automation`](./packages/automation/AGENTS.md) — без отправки уведомлений в этой
  итерации, только фиксация факта в истории.

Правила по ошибкам:

- Единоразовая задача, упавшая с ошибкой → фиксируется как **ошибка**.
- Периодическая задача, у которой конкретная проверка завершилась с ошибкой → в лог пишется, что
  **эта проверка** завершилась ошибкой (сама периодическая задача не считается проваленной).

## Домен: сессии

**Сессия** — набор данных, необходимых воркеру-парсеру для работы с маркетплейсом: куки, заголовки,
данные о прокси. Сессии генерирует `worker_sessions`
(см. [`apps/worker_sessions/AGENTS.md`](./apps/worker_sessions/AGENTS.md)), использует `worker_parser`.

Формат хранения и TTL решены: Redis, `session:{marketplace}:{id}` (TTL на ключе) +
`sessions:pool:{marketplace}` (`ZSET` по времени истечения — учёт глубины пула). Условие
невалидности — сессия не проходит валидацию реальным запросом к API маркетплейса перед сохранением
(`worker_sessions` не сохраняет невалидные сессии вовсе).

Протокол получения сессии решён: прямое чтение Redis, не HTTP-ручка — `worker_parser` атомарно
забирает сессию через `SessionPoolStore.acquire_session` (`ZPOPMIN` по `sessions:pool:{marketplace}`,
общий с `worker_sessions` класс в [`packages/sessions`](./packages/sessions/AGENTS.md)).

## Домен: пользователи и тарифы

Роли:

- **Клиент** — доступ через фронтенд (постановка задач) и/или напрямую через API.
- **Администратор** — управляет тарифами/квотами пользователей и сроком хранения результатов
  периодических задач.

Квоты на частоту парсинга задаются не воркерам, а **пользователям** — в виде тарифов, которые выдаёт
администратор.

## Архитектура

Подробности — в [`docs/reference/architecture.md`](./docs/reference/architecture.md).

Коротко: `api` создаёт задачи → задачи попадают в очередь, реализованную поверх таблиц PostgreSQL →
для периодических задач планировщик (scheduler) регулярно ставит их в очередь заново → `worker_parser`
забирает задачи из очереди и для их выполнения запрашивает сессию у `worker_sessions` → `worker_parser`
периодически отправляет HTTP heartbeat с своим статусом, текущими задачами и готовностью принимать новые.

Миграции БД — через **Alembic**.
