# oz_flow: что динамическое, что — слепок, и что может потребовать правок

Дата: 2026-10-07. Относится к безбраузерному получению антибот-кук Ozon
(`apps/worker_sessions/js_runtime/ready/ozon/oz_flow.py`, актуально для `script_v47_2.js`).
Формат самого отпечатка разобран в
[`apps/worker_sessions/js_runtime/ready/ozon/FINGERPRINT.md`](../apps/worker_sessions/js_runtime/ready/ozon/FINGERPRINT.md).

## Что сейчас динамическое, а что — слепок

**Вычисляется заново при каждом прогоне** (живой прогон оригинального скрипта):

- сам челлендж, токен `sc:...`, куки `abt_data`/`__Secure-ETC`;
- **схема fp** (набор секций) — берётся из вывода запущенной VM, поэтому смена v47_4 → v47_2
  пережилась без правок;
- **константы сборки** (`browser_2`, `fn_1..3` со стеками и офсетами) — их считает оригинальный
  байткод;
- динамика челленджа (`challenge.id/checkStr`, `ts`, `nonce`, `pzs`, `pzc`);
- длина цепочки md5, seed, salt;
- метки `performance.timing` — перебазируются на «сейчас» (но структура — из слепка).

**Слепок** (`template_chrome154.json`, снят с настоящего Chrome 154 06.10.2026):

- все секции окружения: `screen_*`, `navigator` (весь список API Chrome 154), `webgl`,
  `canvas`-хэш, `fonts`, `css`, `rtc`, `video`, `props`, `touch`, флаги `browser`, `location`,
  `context`, структура `performance` и размеры heap.

**Захардкожено в коде**:

- UA «Chrome 154» + `sec-ch-ua` + `accept-language`;
- TLS-отпечаток `chrome136` (curl_cffi) — т.е. JA4 ≠ заявленной версии UA, сегодня сервер это
  принимает;
- рецепт кодека (XOR токеном → AES-256-CBC/EvpKDF → seed посередине base64, цепочка md5 1–8
  раундов);
- прокладки окружения в `oz_solve.js` (`env_extra.js`, `env_canvas.js`) и списки полей
  `KEEP`/`VM_DERIVED`;
- `x-o3-app-version` в проверочном запросе.

## Что в теории может измениться и потребовать правок

### 1. Очередная сборка скрипта (`script_vNN_M`) — в основном переживается, но

- добавится **новая секция fp**, которую jsdom заполняет неправдоподобно (например, вернут
  `battery`/`hev`/`media_devices`) — значение останется нашим фейковым → отказ.
  Правка: свежий эталон или мок;
- появится **новая константа сборки** (условный `browser_3`) — уйдёт значение из чужого шаблона.
  Правка: добавить ключ в `VM_DERIVED`;
- **сменится кодек** (другой шифр, другое место seed, иной рецепт пароля сверх 1–8 раундов) —
  `decode` упадёт. Правка: ре-реверс (`brute_chain.js` помогает только с длиной цепочки);
- **антиотладка начнёт детектить jsdom/`node:vm`** (проверки Proxy-глобала, `evalmachine` в
  стеках вне `fn_1`) — VM не дойдёт до `fetch`. Правка: расширять прокладки окружения.

### 2. Старение слепка окружения

- флот Chrome уйдёт вперёд, а шаблон/UA заявляют 154 — Ozon может начать резать старые версии
  или сверять список API в `navigator` с заявленной версией.
  Правка: переснять эталон с нового Chrome + обновить UA/`sec-ch-ua`;
- хуже: для нового impersonate-образа может не оказаться цели в установленной версии curl_cffi →
  апгрейд curl_cffi.

### 3. Транспортный отпечаток (JA3/JA4/HTTP2)

- сегодня chrome136-TLS под UA 154 проходит; если начнут требовать совпадения мажорных версий
  JA4↔UA — понадобится impersonate под 154 (или UA под 136);
- rate-limit на `/abt/result` по IP при массовой генерации (сейчас не проверено) → прокси-путь в
  коде есть, но не тестирован;
- баны датацентровых ASN, переход на HTTP/3 — смена транспорта.

### 4. Изменение самого потока челленджа

- куки начнут ставиться в ответе POST, а не на reload (или добавится шаг) — правка
  `get_ozon_cookies`;
- `checkStr`/`pzs` начнут зависеть от окружения (сейчас — только от челленджа, поэтому
  jsdom-значения принимаются);
- смена формата `#challenge`, хоста `st.ozone.ru` или regex'а URL скрипта;
- **challenge-зависимый canvas/шрифты**: сегодня хэш canvas стабилен между челленджами (проверено
  по эталонам), но если отрисовку начнут сидировать данными челленджа — слепок-хэш перестанет
  подходить, а воспроизвести вывод Skia/ANGLE на `@napi-rs/canvas` нереально — это самый тяжёлый
  сценарий, фактически откат к браузеру;
- поведенческие данные (мышь, тайминги ввода) — сейчас их в fp нет вовсе.

### 5. После выдачи токена (для прода, не для исследования)

- привязка токена к IP/UA при использовании (не проверялась) — парсеру придётся работать с тем
  же прокси и UA, что при генерации;
- неизвестный TTL токена — влияет на глубину пула и `GENERATION_TTL_MS`.

## Резюме

Механика «сборка ↔ челлендж» динамическая, «личина браузера» — слепок. Самые вероятные правки —
ротация сборки с новой секцией (мелкая) и старение Chrome-154-идентичности (средняя); самые
тяжёлые — challenge-seeded canvas и детект jsdom в VM.

## План быстрого дебага и адаптации под изменения

Рабочий каталог — `apps/worker_sessions/js_runtime/` (поток — `ready/ozon/`, отладка — `debug/ozon/`; скрипты `debug/ozon/*.js` читающие `raw/` запускать с cwd `ready/ozon/`). Первый шаг при любом подозрении на
поломку — один прогон с диагностикой:

```
python ready/ozon/oz_flow.py      # verbose: GET / → POST → RELOAD → API check
python debug/ozon/oz_check.py 5    # если нужен процент успеха, а не один срез
```

Дальше — по симптому (порядок совпадает с порядком шагов потока).

### Симптом 0: `no challenge script` (GET / не вернул страницу челленджа)

- Смотрим `status`: 200 вместо 403 — антибот вообще не сработал (IP «чистый», челлендж не нужен:
  тогда куки уже в ответе — проверить `cookies`); 5xx/таймаут — сеть/IP/бан.
- 403, но regex не совпал — изменился HTML или хост скрипта: сохранить тело ответа, поправить
  `SCRIPT_URL_RE` в `oz_flow.py`.

### Симптом 1: `oz_solve.js` падает (`RUN ERR`, `TIMEOUT no fetch`, пустой `error`)

VM не дошла до `fetch` — усилилась антиотладка или детект окружения.

1. `node debug/ozon/oz_trace.js raw/last_challenge.html ready/ozon/cache_script_vNN_M.js` — трасса: какие глобалы
   читает VM (`UNDEF global ...`), на чём падает.
2. Достать недостающее в `env_extra.js` / `env_canvas.js` (прокладки) — цель: довести VM до
   `fetch`, содержимое fp на этом шаге не важно.
3. Если VM вешается в бесконечный цикл — сработала проверка исходников функций (их нельзя
   форматировать/патчить): искать, какая функция проверяется, подсовывать настоящий исходник.

### Симптом 2: фордж падает на `decode` (`forge rc=1`, тело в `raw/failed_body_*.json`)

Сменился кодек или длина цепочки вне 1–8.

1. `node debug/ozon/brute_chain.js` — перебор раундов по всем `failed_body_*`. Нашло N → расширить диапазон
   в `fpcodec.js`.
2. Не нашло → проверить структуру: magic `Salted__` на месте? seed всё ещё 4 hex посередине?
   (`brute_chain.js` печатает magic/seed). Съехал формат контейнера → ре-реверс по настоящему
   захвату (см. «Снятие свежего эталона» ниже + хуки `__enc` в `debug/ozon/hook.js`).

### Симптом 3: `POST /abt/result` → 403 `{"ok":false}` (decode при этом работает)

Сервер расшифровал, но содержимое отвергнуто. Самый частый случай при ротации сборки.

0. **Сначала `evalmachine`**: декодировать `raw/last_vm_body.json` и поискать `evalmachine` в строке
   fp (особенно в `fn_1.stack`). Это маркер `node:vm` → гарантированный 403 (инцидент 2026-10-08:
   подмена URL в стеках не сработала, когда версия сборки совпала с версией шаблона). Фикс живёт в
   `oz_forge.js` — подмена безусловная; если маркер снова есть — сломался именно он.
1. Сверить версию: `script_vNN_M` в выводе vs `ready/ozon/cache_*.js`. Новая версия — почти наверняка
   дрейф схемы или новая константа сборки.
2. Дифф ключей: декодировать своё тело (`fpcodec.js::decode` над `raw/last_vm_body.json`) и
   сравнить `Object.keys` с `template_chrome154.json`. Меньше ключей, чем у шаблона — VM пропустила
   секции из-за отсутствующих в jsdom API (проверить прокладки в `env_extra.js`); новые ключи,
   которых нет в шаблоне — кандидаты на отказ (их значения остались jsdom-ными): снять свежий
   эталон или замокать.
3. Подозрение на новую константу сборки (аналог `browser_2`): сравнить значения своего fp с
   шаблоном по ключам; всё, что по смыслу зашито в байткод (строки-приманки, исходники функций),
   перенести в `VM_DERIVED` в `ready/ozon/oz_forge.js` — значение возьмётся из VM-прогона.
4. Версия та же и схема та же, а 403 начались массово и внезапно — слепок состарился или режут
   транспорт/IP: см. симптом 5 и раздел про JA4 выше; проверить `x-o3-bot-score` и
   `x-o3-antibot-ja4-*` в ответе.

### Симптом 4: POST 200 `{"ok":true}`, но на reload кук нет

Изменился поток материализации токена: смотреть ответ reload (статус, новый челлендж в HTML?),
возможно куки теперь ставит сам POST (тогда убрать reload) или появился промежуточный шаг —
повторить его по HAR из настоящего браузера.

### Симптом 5: куки есть, но API отвечает 403

- `x-o3-app-version` в `check_api` устарел — взять актуальный из настоящего фронта
  (`"appVersion":"..."` в HTML/манифесте), как это делает прод-код.
- Токен привязали к IP/UA: проверить тем же IP и UA — если только так проходит, зафиксировать
  связку (для прода: парсер работает через тот же прокси/UA, что и генерация).

### Снятие свежего эталона (универсальная адаптация под п.1–3)

1. Настоящий Chrome → открыть ozon.ru, в DevTools перехватить тело `POST /abt/result`
   (`{"token","fp","info","error","timings"}`), сохранить JSON.
2. `node -e` с `fpcodec.js::decode(fp, token)` → расшифрованный объект.
3. Сохранить: как `ready/ozon/template_chrome154.json` (общий эталон) **или** сырое тело в
   `ready/ozon/raw/real_script_vNN_M_0.json` (per-build эталон подхватывается автоматически).
4. Заодно обновить `UA`/`CH` в `oz_flow.py` под версию Chrome, с которой снят эталон, и
   impersonate в curl_cffi под ближайшую доступную версию.
5. Контроль: `python debug/ozon/oz_check.py 10` → цель 10/10.

### Чего в плане нет (сценарии «откат к браузеру»)

Challenge-seeded canvas/шрифты (хэш зависит от челленджа — слепок не подставить), детерминированный
детект jsdom внутри VM, обязательные поведенческие данные. Диагностируются через симптом 3
(всё сходится, а сервер не принимает). Выход — возврат на Camoufox-путь (прод уже умеет) и
отдельное исследование.
