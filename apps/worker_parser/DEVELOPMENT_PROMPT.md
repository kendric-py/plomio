# Промт для разработки apps/worker_parser

Разработай `apps/worker_parser` — воркер, который забирает задачи парсинга OZON/Wildberries из очереди
и исполняет их. Это отдельный процесс монорепо SMPCrawl (`C:\Users\kendric\Desktop\monosmp`).

## Контекст, который нужно изучить перед проектированием

1. `packages/task/` (`AGENTS.md` + `src/`) — уже реализованная доменная область очереди задач.
   Прочитай `packages/task/AGENTS.md` и `packages/task/src/*` целиком — это контракт, вокруг
   которого строится воркер, не придумывай свою модель очереди заново:
   - `TaskRepository.claim_next(worker_id, lease_duration)` — забор задачи (`SELECT ... FOR UPDATE
     SKIP LOCKED`, приоритет/TTL уже учтены).
   - `TaskRepository.heartbeat(task_id, worker_id, lease_duration)` — обязателен периодический вызов,
     пока воркер обрабатывает задачу, иначе аренда протухнет и `reclaim_expired_leases` вернёт задачу
     в очередь параллельно с тем, что этот воркер всё ещё её обрабатывает. **Не путать** с HTTP-
     heartbeat самого процесса воркера — см. отдельный раздел ниже, это два независимых механизма.
   - `TaskService.record_item_progress(item_id, cursor, result_count)` — курсор пагинации ОБЯЗАН
     персиститься сюда по ходу работы (после каждой страницы/батча), а не только при ошибке.
   - `TaskService.complete_item(item_id, status, error_reason)` — терминальный статус одного входа
     (SUCCEEDED/FAILED); сервис сам пересчитывает статус родительской задачи.
   - `TaskItem.cursor` — JSONB, непрозрачен для домена, форму определяет воркер.
   - `ParseType`: `PRODUCT_PAGE` (известное кол-во входов), `SEARCH_QUERY`/`REVIEWS`/`CATEGORY`/
     `SELLER` (пагинация, неизвестный итог).
2. Корневой `AGENTS.md`, `docs/reference/architecture.md`, `docs/reference/backend.md` — общая
   архитектура. Heartbeat-протокол получателя всё ещё помечен как TODO — закрой его в ходе этой
   задачи либо явно зафиксируй как открытый вопрос с вариантами, не придумывай тихо. Протокол
   worker_parser ↔ worker_sessions — **частично решён**: сторона хранения (`worker_sessions` →
   Redis) уже реализована и не переделывается, см. отдельный раздел ниже.
3. `docs/reference/gold-rules.md` и `docs/reference/anti-patterns.md` — обязательны к соблюдению
   (структура пакета: `AGENTS.md` + `src/`, `enums.py` отдельно, `Field(...)` на каждом pydantic-поле,
   никаких вложенных функций/импортов внутри функций/сокращённых имён/позиционных аргументов).
4. `core/repository.py`, `core/transaction_manager.py` — паттерн работы с БД, которому должен
   следовать и воркер (свой `AsyncTransactionManager`, не отдельная сессия).
5. `apps/worker_parser/` — сейчас пустая заготовка (`.env`, `Dockerfile`, `pyproject.toml` с
   зависимостью на локальный `shared`). `AGENTS.md` пустой — обязательно заполнить по итогам работы.

## Референс: `C:\Users\kendric\Desktop\marketplace-parser`

Это отдельный существующий (рабочий) парсер OZON/Wildberries. Забери оттуда ТОЛЬКО прикладную логику
парсинга, не инфраструктуру очереди:

**Переносим и адаптируем:**
- HTTP-фетчеры по типам (`src/marketplaces/ozon/fetchers/*`, WB-аналоги): деталка товара, поиск,
  категория, продавец, отзывы — запросы, заголовки, извлечение данных из ответа маркетплейса.
- Логику пагинации (`_pagination.py`: `extract_next_page` и подобное) и извлечения/дедупликации
  товаров (`extract_product_list`, `seen_keys`).
- Использование `curl_cffi` как HTTP-клиента (или обоснованно предложи замену, если для монорепо
  разумнее async-клиент, согласованный с остальным стеком — реши и обоснуй, не копируй бездумно).

**НЕ переносим as-is, а переосмысливаем под `packages/task`:**
- `resume_state` в `marketplace-parser` — эфемерный, живёт в памяти на время retry внутри процесса
  и теряется при падении воркера (см. `src/worker/sub_job.py::run_sub_job_with_resume`,
  `PartialResultError`). В этом проекте курсор ОБЯЗАН быть персистентным — писать его в
  `TaskItem.cursor` через `TaskService.record_item_progress` после каждой успешно обработанной
  страницы/батча, чтобы `reclaim_expired_leases` (детект упавшего воркера) не терял прогресс.
- Очередь на RabbitMQ (`aio_pika`, `src/entrypoints/worker.py`) — не переносится вообще, у нас
  своя Postgres-очередь через `TaskRepository.claim_next`. Воркер должен быть poll-луп (или
  LISTEN/NOTIFY, если решишь, что это оправдано), а не consumer очереди сообщений.
- Трёхуровневая retry/escalation-лестница (`src/worker/execution.py`) — сама идея ретраев/смены
  сессии при бане может быть переиспользована по смыслу, но должна опираться на персистентный
  курсор из `TaskItem`, а не на `resume_state`, передаваемый через исключение.
- `TaskModel`/`data_manager` — своя модель БД marketplace-parser, не используется; всё хранение
  оркестрации — через `packages/task`.

## HTTP-heartbeat воркера (liveness), отдельно от lease-heartbeat задачи

Воркер обязан раз в N секунд отправлять HTTP-запрос на бекенд, сообщающий, что он жив (процесс-
уровневый liveness-сигнал, не привязан к конкретной обрабатываемой задаче — отправляется, даже пока
воркер простаивает без задач). Это отдельный от `TaskRepository.heartbeat` механизм.

Что уже решено:
- **Имя воркера обязательно берётся из `.env`** (например `WORKER_NAME`) через `pydantic-settings`,
  по аналогии с `core/configs.py`/`apps/api/src/config.py` — не генерируется рантаймом (не hostname,
  не PID), значение конфигурируется явно при деплое каждого инстанса воркера, и именно оно
  передаётся в теле/параметрах liveness-запроса как идентификатор воркера.
- **В каждом heartbeat-запросе воркер обязан отдавать и свой статус**, минимум три значения (заведи
  под это enum в новом домене, по аналогии с `TaskStatus`/`TaskItemStatus` в `packages/task/src/enums.py`):
  - **готов к работе** — простаивает, может забрать новую задачу (`claim_next` вернул бы результат);
  - **работает** — сейчас обрабатывает задачу (`claim_next` уже что-то вернул, воркер занят);
  - **ожидает прокси** — заблокирован на получении сессии из Redis, наполняемого `worker_sessions`
    (см. раздел про `apps/worker_sessions` и стратегию потребления ниже), и не может ни взять новую
    задачу, ни продолжить текущую, пока не получит сессию.
  Список статусов не обязательно закрытый — если в ходе проектирования понадобится больше состояний
  (например, отдельно «завершает работу»/«ошибка сессии»), предложи их, но эти три — обязательный
  минимум.

Что ещё НЕ решено — зафиксировать как открытый вопрос и предложить варианты, а не придумывать тихо:
- Адрес/эндпоинт на бекенде, принимающий этот HTTP-запрос (`apps/api` напрямую? отдельный роут?).
- Остальной формат тела запроса помимо имени воркера и статуса (текущие задачи, их количество и т.п.,
  как намекает `docs/reference/architecture.md`, или ограничиться именем+статусом на этой итерации?).
- Значение N (периодичность) — конфигурируемое через `.env` или константа.
- Что происходит на бекенде при пропуске нескольких heartbeat подряд (TODO в `architecture.md`,
  этот же вопрос).

## `apps/worker_sessions` уже реализован и работает — читай его контракт, не изобретай заново

`apps/worker_sessions` (генерация кук/заголовков/прокси через Camoufox) **больше не пустая
заготовка** — реализован и рабочий. Прочитай `apps/worker_sessions/AGENTS.md` целиком перед
проектированием, это готовый контракт хранения:

- Данные сессии — `session:{marketplace}:{session_id}` в Redis, значение — JSON (`SessionMessage`:
  `cookies`, `user_agent`, `sec_ch_ua`, `sec_ch_ua_platform`, `proxy`, `extra`), с `PEXPIRE` на TTL
  (по умолчанию 7 минут, `GENERATION_TTL_MS`). Ключ исчезает сам по истечении TTL — не читай
  просроченную сессию как валидную, полагайся на TTL, а не на поле внутри JSON.
- `sessions:pool:{marketplace}` — `ZSET`, score = `expire_at` (unix-время); `worker_sessions`
  использует его для учёта глубины пула, но это тот же ключ, из которого `worker_parser` может
  забирать сессии (см. вопрос про стратегию потребления ниже).
- `{SESSIONS_STREAM_PREFIX}:{marketplace}` (по умолчанию `sessions:ozon` / `sessions:wildberries`)
  — Redis Stream, отдельный канал-уведомление на маркетплейс (`XADD` при каждом сохранении сессии,
  запись — `session_id`+`expire_at`, `MAXLEN ~` ограничивает рост при отсутствии потребителя). Это
  **дополнение** к TTL-хранилищу, не замена: источник истины по валидности сессии — TTL на
  `session:{marketplace}:{id}`, у записей в Stream своего TTL нет.
- Подключение к Redis — глобальный `RedisConfig` в `core/configs.py` (`config.REDIS`), не отдельная
  настройка воркера — переиспользуй его.

**Не решено и остаётся на этой задаче:** как именно `worker_parser` **потребляет** сессию из
Redis — не придумывай тихо, зафиксируй как открытый вопрос и предложи варианты, например:
- `ZPOPMIN sessions:pool:{marketplace}` — атомарно забрать сессию с ближайшим `expire_at` и сразу
  убрать её из пула (никакой другой воркер её не возьмёт), с проверкой на стороне `worker_parser`,
  что до истечения TTL остаётся достаточный запас времени на обработку задачи, иначе — забрать
  следующую;
- `XREADGROUP` по стриму `{SESSIONS_STREAM_PREFIX}:{marketplace}` с consumer group — потребление
  без поллинга (`XREAD BLOCK`), но запись в стриме не удаляется автоматически при обработке и не
  гарантирует, что сессия ещё не протухла на момент чтения (нужна повторная проверка TTL/`GET` по
  `session:{marketplace}:{id}` перед использованием);
- что-то ещё, если видишь более удачный вариант, — обоснуй выбор.

## Формат работы

Зайди в Plan Mode. Сначала разведай `packages/task`, `apps/worker_sessions` (реализацию и
`AGENTS.md`) и `marketplace-parser` (можно параллельными Explore-агентами), затем задай уточняющие
вопросы по неопределённым местам (эндпоинт HTTP-heartbeat воркера, его периодичность N, остальной
состав тела запроса помимо имени+статуса, стратегия потребления сессии из Redis — `ZPOPMIN` по
пулу или `XREADGROUP` по стриму, формат курсора по типам парсинга, стратегия ретраев, HTTP-клиент
для запросов к маркетплейсам), и только после этого пиши план: структуру `apps/worker_parser/src/`,
poll-луп забора задач, обработчики по `ParseType`, персистентный курсор, lease-heartbeat задачи,
клиент получения сессии из Redis (по выбранной стратегии потребления) и отдельно process-level
HTTP-heartbeat воркера с именем из `.env` и статусом (готов к работе / работает / ожидает прокси),
обработку `PAUSED`/`CANCELLED` (кооперативная проверка статуса — см. `TaskService`/`AGENTS.md`), и
обновление `apps/worker_parser/AGENTS.md`.
