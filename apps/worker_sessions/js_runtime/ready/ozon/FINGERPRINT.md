# Отпечаток Ozon (fp): принцип составления

Дата: 2026-10-07. Актуально для сборки `script_v47_2.js` (проверено вживую: 10/10 валидных сессий,
`debug/ozon/oz_check.py`). Этот документ описывает, из чего состоит отпечаток, который антибот-скрипт Ozon
собирает и отправляет на сервер, и как `oz_flow.py` + `ready/ozon/oz_forge.js` собирают валидный отпечаток
без браузера.

## 1. Место отпечатка в потоке

```
GET /                     -> 307 /?__rr=1 -> 403 «Antibot Challenge Page»
                             (+ Set-Cookie: __Secure-ETC, abt_data)
                             в HTML: скрытое поле #challenge (~4,7 КБ) и
                             <script src=".../abt-challenge/script_vNN_M.js">
script_vNN_M.js (VM)      -> собирает отпечаток браузера, шифрует в `fp`
POST /abt/result          -> тело {token, fp, info, error, timings}
                             успех: 200 {"ok":true} (кук в ответе НЕТ)
GET /?__rr=1 (reload)     -> 200 (~475 КБ) + Set-Cookie: __Secure-access-token,
                             __Secure-refresh-token, __Secure-user-id, xcid,
                             __Secure-ext_xcid, __Secure-ab-group
```

Поле `token` тела (`sc:<id22>:<blob>`) VM декодирует из `#challenge`; `info` — строка
`{"cookie_enabled":"true"}`; `error` — пустая строка при штатном прогоне; `timings` — дамп
`performance.timing`. Отпечаток — только поле `fp`, дальше речь о нём.

## 2. Контейнер fp (слои формата, снаружи внутрь)

```
fp (строка ~28 КБ)
├─ base64, в СЕРЕДИНУ которого вставлены 4 hex-символа — seed
│   (позиция вставки: (len(fp)-4)/2; код — fpcodec.js::split)
└─ внутри base64: "Salted__" + salt(8 байт) + шифротекст
     AES-256-CBC, ключ/IV = EvpKDF-MD5(password, salt, 48 байт: key 32 + iv 16)
     открытый текст = utf8(JSON), побайтово XOR-нутый повторяющимся `token`
```

`token` — тот самый `sc:...` из тела запроса: он одновременно ключ XOR и часть пароля,
поэтому fp нельзя переслать/расшифровать без своего токена.

### Пароль и цепочка md5

```
a1 = md5(seed)                 (hex)
a2 = md5(a1 + token)
aN = md5(aN-1)                 для N > 2
password = a_rounds
```

Длину цепочки (`rounds`) VM выбирает **на каждый челлендж** — вживую наблюдались 2, 3, 4 и 5
раундов и у настоящего Chromium, и у нашего jsdom-прогона (`fpcodec.js::chainPw`; легаси-имена
v3/v4/v5 = 2/4/5 раундов). Экспериментально установлено (`debug/ozon/oz_check.py` + `FORCE_CHAIN`):

- с цепочкой, которую выбрала сама VM: **10/10** прогонов приняты сервером;
- с принудительной «чужой» цепочкой (6 раундов): **0/3**, `403 {"ok":false}`.

То есть сервер знает ожидаемую длину (выводит из челленджа, который сам и сгенерировал), а выбор
VM в нашем окружении всегда с ней совпадает. Поэтому фордж шифрует **той же цепочкой, что выбрала
VM** (`decode` перебирает 1..8 раундов и находит рабочую по маркеру `{"` в начале JSON).
Заметка из старого отчёта «jsdom выбирает ветку, отличную от браузера» экспериментально не
подтвердилась — по крайней мере для v47_2.

## 3. Внутренний JSON: как сериализован

Это не плоский набор значений, а **глубокий дамп объектной модели браузера** с обходом
прототипных цепочек. Соглашения сериализатора:

- `"@proto:Screen": {...}` — объект получен обходом прототипа `Screen`;
- `"@get:availWidth": 1920` — значение геттера;
- `"@val:dwh": false` — собственное значение;
- строки-заглушки вместо несериализуемого: `"_fn_"` — функция (в т.ч. native), `"_n_"` — null,
  `"_u_"` — undefined, `"_m_"` — свёрнутый объект (цикл/уже встречался).

Именно поэтому jsdom-прогон без подмены бесполезен: в дампе оказываются исходники геттеров jsdom
(`"get availWidth() { const $impl = $requireImpl(..."`), `screen 0×0`, `isChrome:false` — сервер
это видит сразу.

## 4. Состав отпечатка по секциям (схема v47_2, 27 ключей)

Три класса полей и их источник при фордже:

| Секция | Что внутри | Класс | Источник в фордже |
|---|---|---|---|
| `challenge` | `{id: "fab_chlg_…", version: "47_2", checkStr}` из #challenge | динамика челленджа | VM (KEEP) |
| `ts` | `Date.now()` сборки fp | динамика | VM |
| `nonce` | случайная строка | динамика | VM |
| `pzs` | `"sc:<id22>"` — второй токен, выводится VM из челленджа (≠ `token`) | динамика | VM |
| `pzc` | число (наблюдалось 0) | динамика | VM |
| `browser_2` | строка-приманка вида `"Atom v91.197.77"` — зашита в байткод сборки (у v47_3: `"Chrome v205.194.125"`, у v47_4: `"Safari v110.166.232"`); от UA не зависит | **константа сборки** | VM (не шаблон!) |
| `fn_1` | `Function.prototype.toString` + stack-фреймы с URL и офсетами **этой сборки** скрипта | константа сборки | VM, URL `evalmachine.<anonymous>` → настоящий URL скрипта |
| `fn_2`, `fn_3` | проверки исходников функций (`"111111111111111"`, `function Function() { [native code] }`) | константа сборки | VM |
| `user_agent` | `navigator.userAgent` (должен совпадать с HTTP UA) | окружение | шаблон |
| `browser` | флаги `isChrome/isBlink/…` (jsdom: все false → мгновенный отказ) | окружение | шаблон |
| `props` | 15 замеров размеров/позиций через `|` (jsdom: `-1|-1|…`) | окружение | шаблон |
| `screen_1` | дамп прототипа `Screen` | окружение | шаблон |
| `screen_2` | inner/outer размеры окна, rect body, скролл | окружение | шаблон |
| `screen_3` | фокус/visibility документа, дамп `visualViewport` | окружение | шаблон |
| `touch` | наличие тача (десктопный Chrome: false; jsdom: true) | окружение | шаблон |
| `location` | `referrer`, `loc`, `ploc` | окружение | шаблон |
| `context` | наличие `window.chrome`, `opera`, webkit-признаки | окружение | шаблон |
| `navigator` | дамп `Navigator.prototype` (~9 КБ: весь список API Chrome, `connection.downlink/rtt` — у настоящих захватов гуляют, оба варианта правдоподобны) | окружение | шаблон |
| `performance` | дамп `Performance`: `memory`, `navigation`, **`timing` с абсолютными метками и `timeOrigin`** | окружение + время | шаблон, метки перебазируются на текущий прогон (см. ниже) |
| `video` | `canPlayType` по нескольким MIME (`probably/maybe`) | окружение | шаблон |
| `webgl` | расширения и параметры WebGL (jsdom: `{}`) | окружение | шаблон |
| `canvas` | md5 отрисованного канваса — стабилен между челленджами | окружение | шаблон |
| `css` | результаты `matchMedia` по media features | окружение | шаблон |
| `rtc` | список WebRTC-кодеков | окружение | шаблон |
| `fonts` | битмап наличия шрифтов по замерам ширины | окружение | шаблон |
| `timings` | длительность сборки каждой секции (мс) | замеры | наши (реальные, правдоподобные) |
| `ctm` | суммарное время сборки | замеры | наши |

Четыре секции — `battery`, `storage`, `hev` (high-entropy values UAData), `media_devices` —
собираются через **async-API** (`getBattery`, `storage.estimate`,
`userAgentData.getHighEntropyValues`, `enumerateDevices`), которых в jsdom нет: без прокладок VM
их молча пропускает (28 секций вместо эталонных 32). `env_extra.js` содержит прокладки этих API —
тогда VM включает секции, как настоящий Chrome, для любой сборки (проверено: и v47_2, и v47_4
выдают 32 секции). Сервер к их отсутствию толерантен (v47_2 принимал 28 секций 10/10), но мы
сознательно совпадаем с эталоном по набору секций.

## 5. Как фордж собирает валидный fp (`ready/ozon/oz_forge.js`)

1. Прогоняем **оригинальный** скрипт челленджа в Node (`ready/ozon/oz_solve.js`: jsdom + `node:vm` +
   canvas на `@napi-rs/canvas`, `NOWEBGL=1`). VM сама решает челлендж и отдаёт тело с
   зашифрованным fp. Его содержимое по окружению — «jsdom», но динамика и константы сборки —
   настоящие, т.к. их вычислил оригинальный байткод.
2. Расшифровываем fp своего прогона (`fpcodec.js::decode`, перебор раундов 1..8).
3. Собираем выходной JSON:
   - **ключи** — от нашего прогона (схема всегда соответствует сборке, которую отдал сервер);
   - динамика (`challenge, ts, nonce, pzs, pzc`) — наша;
   - константы сборки (`browser_2, fn_1, fn_2, fn_3`) — наши; в стеках `fn_1` **всегда** подменяем
     `evalmachine.<anonymous>` на настоящий URL `script_vNN_M.js` (безусловно — см. инцидент в
     разделе 6). Больше стеки не трогаем: фреймы `node:internal` сервер принимает, а их вырезание
     ломает сессию (инцидент 2026-10-10);
   - `performance` — структура шаблона, но все метки > 1e12 сдвигаются так, чтобы
     `navigationStart ≈ ts − 1,2 с` (нули остаются нулями): сутки-старые таймстемпы рядом со
     свежим `ts` были бы противоречием;
   - остальное (окружение) — из genuine-источника **той же идентичности, что и HTTP-заголовки**:
     пер-захват сборки (`raw/real_script_vNN_M_0.json`) при наличии, иначе общий эталон
     `template_chrome155.json`. HTTP user-agent/`sec-ch-ua` поток выбирает под поданную сборку
     (`oz_flow.identity_for_build`) — см. инцидент 2026-10-10 в разделе 6.
4. Шифруем обратно (`encode`): XOR токеном, AES-256-CBC, тот же salt, **та же цепочка md5, что
   выбрала VM**, seed вставляется на середину base64.
5. `POST /abt/result` → `200 {"ok":true}` → reload `GET /` → полный набор кук. Контроль:
   поисковый API `entrypoint-api.bx/page/json/v2` отвечает 200 (~190 КБ).

Итог: ~2,0–2,2 с на сессию (solve ≈ 1,0 с: холодный Node + jsdom + VM ≈ 300 мс), 10/10 валидных
подряд (`debug/ozon/oz_check.py`), прямое соединение без прокси.

## 6. Что ломается при смене сборки и что делать

Фордж переживает ротацию `script_vNN_M.js` без правок, пока:

- VM по-прежнему доходит до `fetch` в jsdom (новая антиотладка/проверки окружения могут это
  сломать — тогда сначала чинить `oz_solve.js`/`env_extra.js`);
- новая сборка не добавляет секцию, которую jsdom заполняет неправдоподобно (её значение останется
  нашим — `!(k in base)`; если сервер начнёт отвергать — нужен свежий эталон);
- кодек не меняется (другой XOR/шифр/схема seed → `decode` упадёт: смотреть
  `raw/failed_body_*.json`, перебор раундов — `debug/ozon/brute_chain.js`).

Уроки инцидента 2026-10-08 (поток ломался на v47_4 после ротации обратно с v47_2/v47_5):

- **`evalmachine.<anonymous>` в `fn_1.stack`** — маркер `node:vm`, сервер отвергает. Подмена URL в
  стеках изначально срабатывала только при расхождении версий сборки и шаблона; когда Ozon вернул
  сборку, совпадающую с шаблоном (v47_4), маркер утёк → 403. Фикс: подмена **всегда** для
  VM-полей. Диагностика: декодировать `raw/last_vm_body.json` и искать `evalmachine` в строке fp.
- **Секции за async-API** (`battery/storage/hev/media_devices`) VM пропускает молча, если API нет
  в окружении — набор секций перестаёт совпадать с настоящим Chrome. Фикс: прокладки в
  `env_extra.js` (значения всё равно подменяются эталоном при фордже).

Уроки инцидента 2026-10-10 (поток ломался, когда Ozon вернул сборку v47_1; «чинился» свежими
захватами, но сломался снова на v47_3):

- **Пер-захваты эталонов обязаны быть «чистыми»**: снятые обычным Playwright'ом захваты содержат
  `navigator.webdriver=true` и проигрывают проверку сервером (даже настоящий Chromium с ними
  получает 403). Снимать только с `--disable-blink-features=AutomationControlled` (и лучше с
  настоящего Google Chrome, `channel="chrome"`). Проверка перед использованием:
  `@get:webdriver` в `navigator` захвата — `false`.
- **Идентичность HTTP-заголовков должна совпадать с источником окружения fp**: у v47_3 эталон —
  Chrome 154, у v47_1 (свежий захват) — Chrome 155. HTTP UA 155 + fp с UA 154 = стабильный 403.
  Фикс: `oz_flow.identity_for_build()` берёт UA/`sec-ch-ua` из того же источника, что фордж, и
  при расхождении челлендж берётся заново (сборки крутятся между запросами — до 3 попыток).
- **Не «чинить» то, что не проверено**: фреймы `node:internal` в стеках VM-полей по одному только
  виду кажутся маркером Node, но фордж с ними проходит 10/10, а их вырезание даёт стабильный 403.
  Сервер сверяет структуру/контрольную сумму тела — любые лишние правки fp опасны. Менять только
  то, что доказано экспериментом против живого сервера.

Снять свежий эталон окружения: перехватить у настоящего Chrome тело `POST /abt/result`
(`{"token","fp",…}` — скрипт `scripts/ozon/capture_fresh_abt.py` снимает сам, с нужным флагом
и проверкой токена), расшифровать `fpcodec.js::decode`, сохранить JSON как
`template_chrome<NNN>.json` (обновив `TEMPLATE_FP`/`UA`/`CH` в `oz_flow.py`) или сырым телом в
`raw/real_script_vNN_M_0.json` — тогда эталон и идентичность подхватятся автоматически.

## 7. Что не проверялось

Прокси, нагрузка/rate-limit (все прогоны — ≤1 запроса/2 с с одного IP), срок жизни токена,
поведение при параллельных прогонах, JA4-привязка (заголовки `x-o3-antibot-ja4-*` сервер видит —
мы шлём chrome146-TLS под UA Chrome 154/155; до сих пор принималось).
