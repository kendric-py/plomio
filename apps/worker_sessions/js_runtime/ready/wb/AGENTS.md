# js_runtime/ready/wb — рабочий поток Wildberries

Статус (2026-10-07): **работает, рекомендуется к внедрению** (в прод пока не подключён — там Camoufox
≈ 7,5 с на сессию против ~1 с здесь). Один IP, без прокси, ≤1 запроса / 2 с.

Схема: страница-челлендж (HTTP 498) грузит SDK `index-*.js` (не обфусцирован), дальше чистый HTTP:
`POST /__wbaas/challenges/antibot/api/v1/find-frontend-settings` → `solverPath`, `analytics` (для токена
не нужен) → `POST .../api/v1/create-token` с `{}` → **498** `{challenge:{scriptPath, payload}}`
(payload ≈ 8 КБ) → скрипт `scriptPath` (`/statics/<hash>.js`, ~208 КБ, VM-обфускатор) решается в Node
(вызов зарегистрированной функции `solve(payload)` → `"<n>|<base64>"`) → повторный `create-token`
с `{"challenge":{scriptPath,payload},"solution":{"payload":"<решение>"}}` → 200 `{secureToken}` →
значение куки `x_wbaas_token`. Заголовки: `X-Guardium-Antibot-Key` (= `data-site-key` со страницы,
статичный), `X-Guardium-Antibot-SDK-Version: js-front-browser/3.1.0`. HTTP через curl_cffi с
идентичностью Firefox 135.

## Что нужно WB от клиента

Единственная обязательная кука — `x_wbaas_token`. Валидность проверялась штатным
`generation/validation.py::validate_session` (главная + реальный поисковый запрос): **12/12** (полный
поток) и **12/12** (lean).

## Токен

Формат `1.1000.<id>.<b64(ip|UA|exp|reusable|…)>.<подпись>`: в нём IP и UA выдачи и срок ≈ **72 ч**
(по метаданным токена; живой срок вживую не проверялся). UA на API-запросах не проверяется (токен с
другим UA → 200), IP привязан — выдавать и использовать через один и тот же прокси.

## Как это получилось (кратко)

- В «голом» jsdom `eval` скрипта падает (`E217/E227`: нет глобалей), а в `node:vm` с Proxy-глобалом
  поверх jsdom-окна (`env_min.js`) скрипт отдаёт валидное решение. Canvas = `null` — сервер не
  придирается. Решение ≈ 220 мс; основная накладная — старт jsdom (первый `require('jsdom')` ≈ 750 мс),
  поэтому постоянный Node-процесс обязателен.
- Чистый Python без JS не пробовали: решение считает байткод VM, реверс не окупается.
- Как нашли, что нужно скрипту: логирующий Proxy поверх глобала (`debug/wb/trace.js`).

## Хрупкость

- SDK `index-yz9dDw8g.js` (хэш Vite — меняется со сборкой), solver `challenge-solver_v1.0.8.js`,
  tracker `behavior-tracker_v1.0.3.js`, SDK `3.1.0`, скрипт челленджа `/statics/94d22af85ae5f449.js`.
  Код берёт `scriptPath` из ответа 498 и от хэшей не зависит; `data-site-key` статичен.
- За время работы (~1 ч, десятки челленджей) `scriptPath` не менялся; частота деплоев WB неизвестна.
- Риски: WB добавит проверки окружения (WebGL/canvas/шрифты) → скрипт в jsdom начнёт бросать `E2xx`
  или токены перестанут валидироваться; смена версии протокола `/api/v1`; приём метрик
  `behavior-tracker`; привязка к TLS-JA3/JA4. Митигация: метрика доли ошибок solve/валидации →
  автоматический откат на Camoufox.

## Вердикт и план внедрения

**Внедрять**: ≈ 1 с против ≈ 7,5 с (~7×), ~170 МБ на Node-процесс. Оценка: 2–3 дня на продакшн +
~0,5 дня/мес поддержки, пока протокол не меняется.

Шаги:
1. Модуль `generation/marketplaces/wb/browserless.py`: HTTP через curl_cffi (socks5h-прокси), решение
   через постоянный Node-процесс (пул N процессов, перезапуск по возрасту/ошибкам).
2. `spa_version` и `device_id` — как сейчас (из `session.py`), сессию отдавать в тот же `SessionMessage`.
3. Фолбэк на Camoufox при ошибке solve/валидации; метрики доли успеха и латентности.
4. Тесты на сохранённых челленджах; конфиг-флаг включения; документация в `apps/worker_sessions/AGENTS.md`.
5. Проверка за реальным прокси и под нагрузкой до включения по умолчанию.
