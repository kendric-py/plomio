# Отпечаток Ozon (fp): принцип составления

Дата: 2026-10-07. Актуально для сборки `script_v47_2.js` (проверено вживую: 10/10 валидных сессий,
`oz_check.py`). Этот документ описывает, из чего состоит отпечаток, который антибот-скрипт Ozon
собирает и отправляет на сервер, и как `oz_flow.py` + `oz/oz_forge.js` собирают валидный отпечаток
без браузера.

## 1. Место отпечатка в потоке

```
GET /                     -> 307 /?__rr=1 -> 403 «Antibot Challenge Page»
                             (+ Set-Cookie: __Secure-ETC, abt_data)
                             в HTML: скрытое поле #challenge (~4,7 КБ) и
                             <script src=".../abt-challenge/script_vNN_M.js">
script_vNN_M.js (VM)      -> собирает отпечаток браузера, шифрует в `fp`
POST /abt/result          -> тело {token, fp, info, error, timings}
                             успех: 200 {"ok":true} (кук в ответе НЕТ)
GET /?__rr=1 (reload)     -> 200 (~475 КБ) + Set-Cookie: __Secure-access-token,
                             __Secure-refresh-token, __Secure-user-id, xcid,
                             __Secure-ext_xcid, __Secure-ab-group
```

Поле `token` тела (`sc:<id22>:<blob>`) VM декодирует из `#challenge`; `info` — строка
`{"cookie_enabled":"true"}`; `error` — пустая строка при штатном прогоне; `timings` — дамп
`performance.timing`. Отпечаток — только поле `fp`, дальше речь о нём.

## 2. Контейнер fp (слои формата, снаружи внутрь)

```
fp (строка ~28 КБ)
├─ base64, в СЕРЕДИНУ которого вставлены 4 hex-символа — seed
│   (позиция вставки: (len(fp)-4)/2; код — fpcodec.js::split)
└─ внутри base64: "Salted__" + salt(8 байт) + шифротекст
     AES-256-CBC, ключ/IV = EvpKDF-MD5(password, salt, 48 байт: key 32 + iv 16)
     открытый текст = utf8(JSON), побайтово XOR-нутый повторяющимся `token`
```

`token` — тот самый `sc:...` из тела запроса: он одновременно ключ XOR и часть пароля,
поэтому fp нельзя переслать/расшифровать без своего токена.

### Пароль и цепочка md5

```
a1 = md5(seed)                 (hex)
a2 = md5(a1 + token)
aN = md5(aN-1)                 для N > 2
password = a_rounds
```

Длину цепочки (`rounds`) VM выбирает **на каждый челлендж** — вживую наблюдались 2, 3, 4 и 5
раундов и у настоящего Chromium, и у нашего jsdom-прогона (`fpcodec.js::chainPw`; легаси-имена
v3/v4/v5 = 2/4/5 раундов). Экспериментально установлено (`oz_check.py` + `FORCE_CHAIN`):

- с цепочкой, которую выбрала сама VM: **10/10** прогонов приняты сервером;
- с принудительной «чужой» цепочкой (6 раундов): **0/3**, `403 {"ok":false}`.

То есть сервер знает ожидаемую длину (выводит из челленджа, который сам и сгенерировал), а выбор
VM в нашем окружении всегда с ней совпадает. Поэтому фордж шифрует **той же цепочкой, что выбрала
VM** (`decode` перебирает 1..8 раундов и находит рабочую по маркеру `{"` в начале JSON).
Заметка из старого отчёта «jsdom выбирает ветку, отличную от браузера» экспериментально не
подтвердилась — по крайней мере для v47_2.

## 3. Внутренний JSON: как сериализован

Это не плоский набор значений, а **глубокий дамп объектной модели браузера** с обходом
прототипных цепочек. Соглашения сериализатора:

- `"@proto:Screen": {...}` — объект получен обходом прототипа `Screen`;
- `"@get:availWidth": 1920` — значение геттера;
- `"@val:dwh": false` — собственное значение;
- строки-заглушки вместо несериализуемого: `"_fn_"` — функция (в т.ч. native), `"_n_"` — null,
  `"_u_"` — undefined, `"_m_"` — свёрнутый объект (цикл/уже встречался).

Именно поэтому jsdom-прогон без подмены бесполезен: в дампе оказываются исходники геттеров jsdom
(`"get availWidth() { const $impl = $requireImpl(..."`), `screen 0×0`, `isChrome:false` — сервер
это видит сразу.

## 4. Состав отпечатка по секциям (схема v47_2, 27 ключей)

Три класса полей и их источник при фордже:

| Секция | Что внутри | Класс | Источник в фордже |
|---|---|---|---|
| `challenge` | `{id: "fab_chlg_…", version: "47_2", checkStr}` из #challenge | динамика челленджа | VM (KEEP) |
| `ts` | `Date.now()` сборки fp | динамика | VM |
| `nonce` | случайная строка | динамика | VM |
| `pzs` | `"sc:<id22>"` — второй токен, выводится VM из челленджа (≠ `token`) | динамика | VM |
| `pzc` | число (наблюдалось 0) | динамика | VM |
| `browser_2` | строка-приманка вида `"Atom v91.197.77"` — зашита в байткод сборки (у v47_3: `"Chrome v205.194.125"`, у v47_4: `"Safari v110.166.232"`); от UA не зависит | **константа сборки** | VM (не шаблон!) |
| `fn_1` | `Function.prototype.toString` + stack-фреймы с URL и офсетами **этой сборки** скрипта | константа сборки | VM, URL `evalmachine.<anonymous>` → настоящий URL скрипта |

| `screen_3` | фокус/visibility документа, дамп `visualViewport` | окружение | шаблон |
| `touch` | наличие тача (десктопный Chrome: false; jsdom: true) | окружение | шаблон |
| `location` | `referrer`, `loc`, `ploc` | окружение | шаблон |
| `context` | наличие `window.chrome`, `opera`, webkit-признаки | окружение | шаблон |

`media_devices` — в v47_2 их убрали. **Схема дрейфует между сборками**, поэтому набор ключей
фордж берёт у своего VM-прогона (см. ниже), а не из шаблона.

## 5. Как фордж собирает валидный fp (`oz/oz_forge.js`)

1. Прогоняем **оригинальный** скрипт челленджа в Node (`oz/oz_solve.js`: jsdom + `node:vm` +
   canvas на `@napi-rs/canvas`, `NOWEBGL=1`). VM сама решает челлендж и отдаёт тело с
   зашифрованным fp. Его содержимое по окружению — «jsdom», но динамика и константы сборки —
   настоящие, т.к. их вычислил оригинальный байткод.
2. Расшифровываем fp своего прогона (`fpcodec.js::decode`, перебор раундов 1..8).
3. Собираем выходной JSON:
   - **ключи** — от нашего прогона (схема всегда соответствует сборке, которую отдал сервер);
   - динамика (`challenge, ts, nonce, pzs, pzc`) — наша;
   - константы сборки (`browser_2, fn_1, fn_2, fn_3`) — наши; в стеках `fn_1` подменяем
     `evalmachine.<anonymous>` на настоящий URL `script_vNN_M.js`;
   - `performance` — структура шаблона, но все метки > 1e12 сдвигаются так, чтобы
     `navigationStart ≈ ts − 1,2 с` (нули остаются нулями): сутки-старые таймстемпы рядом со
     свежим `ts` были бы противоречием;
   - остальное (окружение) — из эталонного дампа настоящего Chrome 154
     (`template_chrome154.json`; для сборки, с которой есть настоящий захват
     `raw/real_script_vNN_M_0.json`, — из него).
4. Шифруем обратно (`encode`): XOR токеном, AES-256-CBC, тот же salt, **та же цепочка md5, что
   выбрала VM**, seed вставляется на середину base64.
5. `POST /abt/result` → `200 {"ok":true}` → reload `GET /` → полный набор кук. Контроль:
   поисковый API `entrypoint-api.bx/page/json/v2` отвечает 200 (~190 КБ).

Итог: ~2,0–2,2 с на сессию (solve ≈ 1,0 с: холодный Node + jsdom + VM ≈ 300 мс), 10/10 валидных
подряд (`oz_check.py`), прямое соединение без прокси.

## 6. Что ломается при смене сборки и что делать

Фордж переживает ротацию `script_vNN_M.js` без правок, пока:

- VM по-прежнему доходит до `fetch` в jsdom (новая антиотладка/проверки окружения могут это
  сломать — тогда сначала чинить `oz_solve.js`/`env_extra.js`);
- новая сборка не добавляет секцию, которую jsdom заполняет неправдоподобно (её значение останется
  нашим — `!(k in base)`; если сервер начнёт отвергать — нужен свежий эталон);
- кодек не меняется (другой XOR/шифр/схема seed → `decode` упадёт: смотреть
  `raw/failed_body_*.json`, перебор раундов — `oz/brute_chain.js`).

Снять свежий эталон окружения: перехватить у настоящего Chrome тело `POST /abt/result`
(`{"token","fp",…}`), расшифровать `fpcodec.js::decode`, сохранить JSON как
`template_chrome154.json` (или сырым телом в `raw/real_script_vNN_M_0.json` — тогда эталон и
цепочка подхватятся автоматически).

## 7. Что не проверялось

Прокси, нагрузка/rate-limit (все прогоны — ≤1 запроса/2 с с одного IP), срок жизни токена,
поведение при параллельных прогонах, JA4-привязка (заголовки `x-o3-antibot-ja4-*` сервер видит —
мы шлём chrome136-TLS под UA Chrome 154; до сих пор принималось).
