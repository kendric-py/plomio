# Ozon: получение антибот-кук без браузера — итог исследования

Дата: 2026-10-07. Статус: **безбраузерный путь РАБОТАЕТ** (проверено на `script_v47_2.js`: 10/10
валидных сессий подряд, `oz_check.py`). Прод-код не менялся; в проде пока Camoufox (≈ 5 с на сессию).
**Полный разбор формата отпечатка и принципа форджа — в [`oz/FINGERPRINT.md`](./oz/FINGERPRINT.md).**

## Рабочий путь (`python oz_flow.py`)
1. `curl_cffi` (impersonate chrome136) `GET /` → страница челленджа, скрипт `script_vNN_M.js`.
2. Node (`oz/oz_solve.js`, jsdom) прогоняет оригинальный скрипт и формирует тело `POST /abt/result`.
3. `oz/oz_forge.js` расшифровывает `fp` (`oz/fpcodec.js`) и собирает его заново: **схема (набор ключей)
   и константы сборки (`browser_2`, `fn_1..3`) — от своего VM-прогона**, динамика челленджа
   (`challenge,ts,nonce,pzs,pzc`) — своя, метки `performance.timing` перебазируются на текущий запуск,
   остальное окружение — из эталонного дампа настоящего Chrome 154 (`template_chrome154.json`; для
   сборки с настоящим захватом — `raw/real_script_vNN_M_0.json`). Шифрует обратно **той же цепочкой
   md5, что выбрала VM** (2–5 раундов; чужая цепочка сервером отвергается — проверено: r6 → 0/3).
4. `POST /abt/result` → `200 {"ok":true}`. **Куки в этом ответе не приходят — нужен повторный `GET /`**:
   он отдаёт 200 (≈475 КБ) и `__Secure-access-token`, `refresh-token`, `user-id`, `ab-group`,
   `ext_xcid`, `xcid`.
5. Проверка: `entrypoint-api.bx/page/json/v2` (поиск «телефон») → 200, JSON ~190 КБ.
Тайминг: ≈ 2,05 с на сессию в среднем (solve ≈ 1,0 с, холодный Node; ~175 МБ RSS). Прямое соединение.
Не проверено: прокси, нагрузка, срок жизни токена. Смена версии скрипта: пережита без правок при
переходе v47_4 → v47_2 (схема у сборок разная — v47_2 убрал `battery/storage/hev/media_devices`);
что делать при будущих сменах — раздел 6 в `oz/FINGERPRINT.md`.
Ниже — исторический отчёт до этого шага (его выводы про отказ сервера устарели).


## Что требуется от клиента
Куки `abt_data`, `__Secure-ETC`, `__Secure-access-token` (+ опционально `__Secure-refresh-token`, `__Secure-user-id`,
`__Secure-ext_xcid`). Без `__Secure-access-token` сессия не проходит API (403 «Antibot Captcha»).

## Что было проверено

### 1. Механика челленджа
- `GET /` → 307 `/?__rr=1` (ставит `__Secure-ETC`, `abt_data`) → 403 «Antibot Challenge Page».
- Страница грузит скрипт `https://st.ozone.ru/s3/abt-challenge/script_vNN_M.js` (≈ 112 КБ). Во время работы **одновременно
  отдавались две сборки: `v47_4` и `v47_3`** (`Last-Modified` для `v47_4` — 2026-08-03). Скрипт — байткод-VM с встроенными
  криптопримитивами и антиотладкой (`debugger`, проверки исходников функций → бесконечный цикл; код нельзя форматировать).
- Скрипт собирает отпечаток браузера и отправляет `POST /abt/result` с полями `token`, `fp`, `info`, `error`, `timings`.
  Успех → `200 {"ok":true}` и куки; отказ → `403 {"ok":false}` без подробностей.
- Заголовки ответа содержат `x-o3-bot-score` и `x-o3-antibot-ja4-*`: серверу виден TLS/HTTP-fingerprint клиента.

### 2. Состав отпечатка (по реальному захвату Chrome 154)
Это не набор отдельных значений, а **глубокий дамп объектной модели браузера**: `screen`, `visualViewport`, `navigator`
(включая весь список API Chrome), `userAgentData`, плагины/MIME-типы, `window.chrome`, батарея, хранилище, медиа-устройства,
`performance`, WebGL (расширения, параметры), canvas-хэш, шрифты, WebRTC-кодеки, CSS media features, замеры размеров и времён, плюс
служебные поля (id челленджа, версия сборки, контрольные значения). Часть полей — константы сборки скрипта, часть — динамика
(время, случайные числа, размеры окна).

### 3. Запуск оригинального скрипта в лёгком рантайме (Node + jsdom)
- Скрипт доходит до конца и формирует `fp` (≈ 28 КБ), **но сервер отвечает 403 `{"ok":false}`**.
- В дампе окружения у jsdom видно, что это не браузер: исходный код геттеров вместо `[native code]`, экран 0×0, флаги
  `isChrome/isFirefox = false`, нет асинхронных API (`getBattery`, `storage.estimate`, `enumerateDevices`…), нет WebGL.
- Побочно: заглушка WebGL ломала вычисление `fp` целиком (в этих прогонах `fp` пустой) — все эксперименты с ней невалидны.

### 4. Разделение «транспорт или содержимое»
Тело, собранное в моём окружении, было отправлено **из настоящего Chromium** (родные TLS, заголовки, куки): ответ всё равно
`403 {"ok":false}`. Значит, отказ определяется **содержимым отпечатка**, а не клиентом HTTP.
Контроль: штатный Chromium (в т.ч. с логирующим патчем скрипта) проходит, `x-o3-bot-score: 10`.

### 5. Дополнительные наблюдения
- Формат передачи отпечатка зависит от сборки скрипта и от конкретного челленджа (параметры шифрования отличаются между сборками
  и даже между челленджами одной сборки); в окружении jsdom VM может выбирать иную ветку, чем в настоящем браузере.
- `x-o3-bot-score` у отклонённых запросов такой же (10), как у принятых — это оценка транспорта, а не отпечатка.
- Несколько попыток подставить в запрос данные, снятые с настоящего браузера, сервер отвергал.
