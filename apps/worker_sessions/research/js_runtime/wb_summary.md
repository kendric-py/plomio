# Wildberries: получение антибот-токена без браузера — итог

Дата: 2026-10-06. Статус: **работает, рекомендуется к внедрению**. Прод-код не менялся; всё лежит в
`apps/worker_sessions/research/js_runtime/`. Один IP, без прокси, ≤1 запроса / 2 с.

## Что нужно WB от клиента
Единственная обязательная кука — `x_wbaas_token`. Валидность проверялась штатным
`generation/validation.py::validate_session` (главная + реальный поисковый запрос).

## Как это работает (протокол)
Страница-челлендж (HTTP 498) грузит SDK `index-*.js` (не обфусцирован) и делает чистый HTTP:

1. `POST /__wbaas/challenges/antibot/api/v1/find-frontend-settings` → `solverPath`, `analytics` (для токена не нужен).
2. `POST .../api/v1/create-token` с `{}` → **498** `{challenge:{scriptPath, payload}}` (payload ≈ 8 КБ).
3. Скрипт `scriptPath` (`/statics/<hash>.js`, ~208 КБ, VM-обфускатор) регистрирует функцию в
   `window[Symbol.for(...)]`; вызов `solve(payload)` возвращает строку `"<n>|<base64>"`.
4. `POST create-token` с `{"challenge":{scriptPath,payload},"solution":{"payload":"<решение>"}}` → 200 `{secureToken}`
   → значение куки `x_wbaas_token`.

Заголовки: `X-Guardium-Antibot-Key` (= `data-site-key` со страницы, статичный), `X-Guardium-Antibot-SDK-Version: js-front-browser/3.1.0`.

Токен: `1.1000.<id>.<b64(ip|UA|exp|reusable|…)>.<подпись>`; в нём IP и UA выдачи и срок ≈ **72 ч**
(по метаданным токена; живой срок не проверялся). UA на API-запросах не проверяется (токен с другим UA → 200), IP, судя по
токену, привязан — выдавать и использовать через один и тот же прокси.

## Как этого добились
Три подхода из задачи:
- **(а) оригинальный JS в лёгком рантайме — сработал.** В «голом» jsdom `eval` скрипта падает (`E217/E227`: нет глобалей),
  а в `node:vm` с Proxy-глобалом поверх jsdom-окна (`wb/env_min.js`) скрипт отдаёт валидное решение. Canvas = `null` — сервер не
  придирается. Само решение ≈ 220 мс; основная накладная — старт jsdom (первый `require('jsdom')` ≈ 750 мс), поэтому нужен
  **постоянный Node-процесс**.
- **(б) чистый Python без JS — не пробовал:** решение считает байткод VM, реверс не окупается.
- **(в) гибрид — финальная схема:** HTTP делает curl_cffi (TLS `firefox135`), JS только вычисляет `solve(payload)`
  (`wb_flow_warm.py` + `wb/solve_server.js`, JSON-lines по stdin/stdout).

Как нашли, что нужно скрипту: логирующий Proxy поверх глобала (`wb/trace.js`) показал, какие глобали он трогает.

## Как воспроизвести
```
cd apps/worker_sessions/research/js_runtime && npm i      # jsdom, js-beautify, @napi-rs/canvas
python wb_flow_warm.py          # 4 токена, тайминги
python wb_validate.py 12 [lean] # N сессий + валидатор приложения
python wb_reuse.py              # один токен × 12 запросов
```
Чистовой сквозной пример «токен → поисковый API → поток названий» (из корня репозитория):
`python scripts/wb/search_stream.py` — спрашивает запрос и печатает названия товаров страница за
страницей раз в секунду (проверено 2026-10-07: 33 страницы / 3297 названий на «наушники», включая
живую деградацию сессии на 33-й странице с автоматической перевыдачей токена и продолжением).

## Хрупкость
- SDK `index-yz9dDw8g.js` (хэш Vite — меняется со сборкой), solver `challenge-solver_v1.0.8.js`, tracker
  `behavior-tracker_v1.0.3.js`, SDK `3.1.0`, скрипт челленджа `/statics/94d22af85ae5f449.js`.
  Наш код берёт `scriptPath` из ответа 498 и от хэшей не зависит; `data-site-key` статичен.
- За время работы (~1 ч, десятки челленджей) `scriptPath` не менялся. Частота деплоев WB неизвестна.
- Риски: WB добавит проверки окружения (WebGL/canvas/шрифты) → скрипт в jsdom начнёт бросать `E2xx` или токены перестанут
  валидироваться; смена версии протокола `/api/v1`; приём метрик `behavior-tracker`; привязка к TLS-JA3/JA4.
  Митигация: метрика доли ошибок solve/валидации → автоматический откат на Camoufox.

## Что не проверено
Работа за реальным прокси и под нагрузкой; живой срок жизни токена; RAM Camoufox для сравнения; поведение при rate limit WB.

## Вердикт и план внедрения
**Внедрять.** ≈ 1 с против ≈ 7,5 с (примерно в 7 раз быстрее), ~170 МБ на Node-процесс. Оценка: 2–3 дня на продакшн-реализацию +
~0,5 дня/мес поддержки, пока протокол не меняется.

Шаги:
1. Модуль `generation/marketplaces/wb/browserless.py`: HTTP через curl_cffi (socks5h-прокси), решение через постоянный
   Node-процесс (пул N процессов, перезапуск по возрасту/ошибкам).
2. `spa_version` и `device_id` — как сейчас (из `session.py`), сессию отдавать в тот же `SessionMessage`.
3. Фолбэк на Camoufox при ошибке solve/валидации; метрики доли успеха и латентности.
4. Тесты на сохранённых челленджах; конфиг-флаг включения; документация в `apps/worker_sessions/AGENTS.md`.
5. Проверка за реальным прокси и под нагрузкой до включения по умолчанию.
